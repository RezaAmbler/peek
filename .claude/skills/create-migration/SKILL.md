# Create an Alembic migration

PEEK uses async SQLAlchemy 2.0 with Alembic migrations in `backend/migrations/`, against SQLite (`data/peek.db`, WAL mode). Run after adding/changing a model in `backend/app/models/`.

## Steps

1. **Confirm the model change is saved** and imported where Alembic's `env.py` collects metadata (a new model file must be importable so autogenerate sees it).

2. **Generate the revision** (from `backend/`, with the venv active):
   ```bash
   cd backend && alembic revision --autogenerate -m "<short description>"
   ```

3. **Review the generated file** in `backend/migrations/versions/` before applying — autogenerate is not trustworthy on SQLite:
   - SQLite can't `ALTER` columns the way Postgres can; column drops/renames/type changes often need Alembic **batch mode** (`with op.batch_alter_table(...)`). Add it if the autogenerated op would fail.
   - Remove spurious ops (e.g. it may try to re-create indexes or miss server defaults).
   - Confirm `upgrade()` **and** `downgrade()` are both correct.

4. **Apply it:**
   ```bash
   cd backend && alembic upgrade head
   ```
   The DB is live at `data/peek.db`. Back it up first if it holds real scan data: `cp data/peek.db data/peek.db.bak`.

5. **Verify**: check the new schema (`sqlite3 data/peek.db ".schema <table>"`), and run `make test-backend` to confirm models still load.

## Notes
- Note that the `backend/.env` and `data/*.db*` files are protected by deny rules — that's expected; the migration tools write to the DB via Alembic, not via direct edits.
- If autogenerate produces nothing but you changed a model, the model probably isn't imported into Alembic's metadata — fix the import and regenerate.
